# Paper-trade simulator для Polymarket — план реализации

Статус: **план, код не написан**. Ждёт ревью по спорным пунктам (раздел 7).

Цель проекта — не «заработать в симуляции», а измерить **знаменатель**: как часто
в live-подрынках Dota 2 / CS2 вообще возникает условие входа. Всё остальное
(PnL, политики выхода) — производное и должно пересчитываться офлайн из
собранных сырых величин.

## 2. Процесс и запуск

Один asyncio-процесс, Python 3.11+. Зависимости коллектора: `httpx`,
`websockets`, `pyyaml`, `pydantic`. Анализатор дополнительно: `pandas`, `numpy`.

```
python run_collector.py --config config.yaml
python export_csv.py   --db state/paper.db --out data/
python analyze_paper.py --db state/paper.db
python tools/replay.py --frames captures/2026-09-19T14.jsonl.gz --db /tmp/replay.db
```

Конкурентные задачи внутри процесса:

| задача | период | что делает |
|---|---|---|
| discovery | `market_discovery.poll_s` (45s) | Gamma, реестр рынков, окно подписки |
| ws_shard × N | постоянно | book / price_change / last_trade_price |
| recorder tick | 2s | снапшоты в кольцевой буфер и в плотное окно |
| checkpoint tick | 60s | чекпоинты +5/10/20/40/60 мин |
| resolution | 1h | `clob.polymarket.com/markets/{condition_id}` |
| reconcile | 60s + отложенный проход +5 мин | `data-api /trades` |
| target_wallet | 5 мин | `/activity` по 4 адресам |
| coverage heartbeat | 60s | агрегация в часовые строки + gap_seconds |

Рестарт: реестр рынков, кэш резолюций, открытые события и открытые виртуальные
позиции лежат в SQLite. При старте — переподписка на весь актуальный список и
строка в `gaps` от `last_heartbeat` до `now` с `reason=process_restart`.

## 3. Различение «сделка на уровне» и «отмена заявок» — главная часть

### 3.1 Что даёт WS и чего не даёт

На канале `market` без авторизации доступны: `book` (полный L2-снапшот, `hash`,
`timestamp`), `price_change` (`changes: [{price, side, size}]`, где `size` — это
**новый абсолютный размер уровня**, а не дельта), `last_trade_price`
(`price`, `side`, `size`, `timestamp`), `tick_size_change`.

Ключевой факт: **`price_change` сам по себе неразличим.** Уровень 0.02 с 500
до 0 — это либо съели, либо сняли. Единственный способ различить — коррелировать
сокращение книги с независимым свидетельством сделки.

### 3.2 Алгоритм (реальное время, провизорная классификация)

Состояние на каждый asset: `book`, очередь `pending_reductions`, счётчик
`trade_credits[side][price] -> [(size, ts)]` с TTL.

**На `last_trade_price`:**
1. Нормализовать сторону в «какая сторона книги пострадала». Сторона тейкера
   SELL → выбиты биды на `price`.
2. `credits[BID][price] += size`, ts запомнить.
3. Немедленно погасить подходящие `pending_reductions` (сделка пришла раньше
   обновления книги — порядок не гарантирован).
4. Если `price <= entry.price`, сторона SELL и у нас лежит виртуальная
   заявка — **вход срабатывает сразу**, `trigger=trade_at_level`. Ждать
   подтверждения книгой нельзя: потеряем состояние «непосредственно до».

**На `price_change` по биду, уровень L, новый размер S:**
- `Δ = old − S`. Если `Δ <= 0` — это добавление, пишем `size_added_at_L`
  (нужно для очереди «позади нас»).
- Если `Δ > 0` — кладём `PendingReduction(L, Δ, ts)` в очередь с дедлайном
  `ts + classify.window_ms` (дефолт 1500). Пытаемся погасить немедленно.

**На дедлайне:**
```
traded    = min(Δ_remaining, доступные кредиты на L в окне ±window_ms)
cancelled = Δ_remaining − traded
```
Пишем строку классификации с `evidence` ∈ {ws_trade, sweep_inferred, none}.

**На `book` (полный снапшот):** состояние сбрасывается, все висящие
`pending_reductions` закрываются как `unknown` — через снапшот классифицировать
нельзя. Счётчик `classify_unknown` — это метрика качества данных, она идёт в
`coverage`.

### 3.3 Три известные дыры и что с ними

**(а) Свип через несколько уровней.** Тейкер, проходящий книгу сверху вниз,
порождает несколько филлов по ценам мейкеров, а `last_trade_price` может
отдать одно сообщение с одной ценой. Тогда сокращения на уровнях ниже
останутся без кредита и будут помечены как отмена — ложно.
Смягчение: если в **одном** сообщении `price_change` сокращён непрерывный
диапазон бидов сверху вниз до уровня L включительно, и на верхней границе
диапазона есть кредит сделки — вся полоса атрибутируется сделке с
`evidence=sweep_inferred`. Это эвристика, не истина, поэтому она живёт в
отдельном поле, а не подменяет `trigger`.

**(б) Двусторонняя отмена.** Маркет-мейкер, снимающий котировки, обычно
трогает обе стороны. Сделка — только одну. Пишем признак
`opposite_side_changed_ms` (сколько мс назад менялась противоположная
сторона). Это **фича для офлайн-анализа**, не правило решения.

**(в) `last_trade_price` может не эмититься на каждый филл.** Утверждать по
памяти, что канал шлёт сообщение на каждую сделку, я не буду. Это проверяется
эмпирически за первые часы (раздел 3.4) и закрывается сверкой.

### 3.4 Самокалибровка стороны на старте

`side` в `last_trade_price` — это сторона тейкера или мейкера, я не полагаюсь
на память. На первых N=200 сделках процесс считает корреляцию: при `side=SELL`
чаще сокращается бид или аск? Результат пишется в `state/calibration.json` и
используется дальше; расхождение логируется. Пока калибровка не набрана,
используется гипотеза «side = сторона тейкера», а события помечаются
`calibration_pending=1`.

### 3.5 Сверка с ончейн-лентой — то, что делает данные доверенными

Раз в 60 секунд и отложенным проходом на +5 минут для каждого рынка с
событиями:

```
GET https://data-api.polymarket.com/trades?market={conditionId}&limit=500&takerOnly=false
```

Дедупликация по (tx_hash, maker, taker, price, size) — при `takerOnly=false`
одна сделка приходит с обеих сторон. Таймстемпы там блочные, с секундной
гранулярностью, поэтому допуск ±3 с, и порядок сделок внутри блока не
восстанавливается.

Для каждого события:
- `trigger=trade_at_level` подтверждено, если в окне есть реальная сделка
  `price <= entry.price` → `trigger_confirmed=1`,
  `confirmed_level_traded_size`;
- `book_vanished` (входа не открывали), но реальная сделка была →
  **ложноотрицательный** классификатор, строка в `reconcile` с
  `verdict=missed_trade`;
- `trade_at_level` без ончейн-подтверждения → `verdict=phantom_trade`.

Анализатор печатает **матрицу ошибок классификатора** как заголовочную
метрику. Если WS-классификация сходится с лентой, скажем, в 97% случаев —
датасету можно верить; если в 70% — весь проект надо пересобирать на ленте, а
не на WS. Без этого числа PnL из симулятора ничего не значит.

### 3.6 Защита от рассинхрона книги

У WS нет пер-ассетных секвенс-номеров, только `hash`, алгоритм которого я
воспроизводить не буду. Вместо этого — периодическая (раз в 5 мин на активный
ассет, с рейт-лимитом) сверка WS-книги с REST-книгой по `token_id`; расхождение
пишется в `book_desync`. Рассинхрон тихо отравляет `prior_size_at_002`, а это
прямо множитель в модели очереди.

## 4. Хранилище: SQLite (WAL) как основное, CSV как экспорт

Схема из ТЗ **сама требует поздних записей в уже написанные строки**:
чекпоинт +60 минут, резолюция, `trigger_confirmed` из сверки,
`target_wallet_traded_here` (кошелёк может зайти в рынок после нашего события).
CSV этого не умеет — получится append-only с патч-строками и грязным merge на
выходе. Плюс: атомарность при падении (оборванная строка CSV = битый файл),
чтение анализатором на живых данных, уникальность `event_id`.

Требование «все новые поля считать при записи» выполняется: производные поля
(`fair_lower_bound`, `book_sum`, `internal_dislocation`, `our_fill`) считаются в
момент записи и хранятся, `export_csv.py` — тупой дамп без пересчёта.

`storage.backend: sqlite | csv` в конфиге, дефолт `sqlite`.

Сырые WS-фреймы: gzip-jsonl **только для окон событий**, хранение
`storage.keep_raw_frames_days: 3`. Это единственный способ переклассифицировать
trade-vs-cancel задним числом, стоит единицы МБ в сутки. Непрерывный лог книги
по всем рынкам — нет, это ровно тот путь, который дал 48 млн снапшотов.

## 5. Окно наблюдения

Сетка плотной записи: `t ∈ {−30, −28, …, +120}` = **76 точек**, не 75
(150 секунд / 2 = 75 интервалов, 76 узлов). Критерий готовности надо читать как
«76», иначе он не выполнится никогда.

Каждое событие несёт `window_complete` и `window_truncated_reason`
(`resolution`, `unsubscribed`, `ws_gap`, `process_stop`) — резолюция на +40 с
даёт легитимно неполное окно, и это не дефект сбора.

Предсобытийная часть (−30…0) берётся из кольцевого буфера (60 с, шаг 2 с).

## 6. Что я реализую иначе, чем в ТЗ, и почему

Упорядочено по тому, насколько сильно пункт угрожает **главному числу**
(частоте события), а не по номерам ТЗ.

### 6.1 Потолок подписок: случайная выборка, НЕ приоритет по ликвидности

Каждый матч CS2/Dota порождает десятки подрынков × 2 токена. 20 параллельных
матчей — потенциально тысячи `asset_id`. Лимиты CLOB WS мне неизвестны, значит
потолок будет. Что делать при переполнении:

- **Неправильно:** ранжировать по ликвидности/объёму. Эффект на 2 центах живёт
  ровно в тонких, никому не нужных подрынках. Отбор по ликвидности выкинет из
  выборки именно ту популяцию, ради которой проект существует, и смещение
  будет направлено против гипотезы.
- **Правильно:** при переполнении — **случайная выборка** среди кандидатов, с
  записью `sampling_rate` и строки на каждый отброшенный рынок в `coverage`.
  Тогда частота экстраполируется корректно.

Молчаливый дроп подписок завышает частоту напрямую: знаменатель сжимается,
числитель нет. Это тот же класс ошибки, что и незалогированный разрыв WS, и
самый вероятный способ получить красивое неверное число.

### 6.2 Определение события — в ТЗ его нет, а без него частота не величина

При обвале по уровню ≤0.02 прилетает пачка сделок. Одно событие или сорок — в
ТЗ не сказано, и от ответа напрямую зависит «срабатываний на рынко-час».

Определение: **событие = жизнь одной виртуальной заявки** от постановки до
полного филла. Не сделка.

- Одна открытая виртуальная заявка на ассет.
- Сделки по уровню, пока у заявки есть остаток, — дофиллы того же события
  (строки в `fills`), а не новые события. `t=0` окна — первый филл.
- После полного филла — `entry.cooldown_s` (дефолт 300) до новой постановки.
- **Все подавленные кулдауном возможности всё равно пишутся** строкой с
  `suppressed_by_cooldown=1`. Тогда частоту можно пересчитать при любом
  кулдауне, включая нулевой, без пересбора. Выбрасывать наблюдение ради
  произвольной константы нельзя.

### 6.3 Три знаменателя, не один

`coverage` получает, помимо `gap_seconds`, ещё две колонки на час/дисциплину:

| знаменатель | смысл |
|---|---|
| `observed_seconds − gap_seconds` | сырая экспозиция: как часто бывает обвал |
| `eligible_seconds` | время, когда держалось предусловие (best_bid ≥ 0.08) |
| `resting_seconds` | время, когда реально лежала виртуальная заявка |

`eligible` и `resting` различаются на кулдаун и на уже открытые позиции.
Частота на сырой рынко-час и частота на час-с-предусловием — ответы на разные
вопросы, и одно без другого неинтерпретируемо.

### 6.4 `prior_size_at_002` — пособытийно, не из снапшота

ТЗ: «в снапшоте непосредственно перед сделкой», при шаге снапшота 2 с. То есть
до 2 секунд устаревания ровно в самый турбулентный момент. Книга ведётся
пособытийно; берётся состояние на последний апдейт **строго до** таймстемпа
сделки. В строку пишется `prior_size_staleness_ms`.

### 6.5 Формула `our_fill` верна — но её легко реализовать неверно

Проверил формулу ТЗ, включая случай несмежного свипа (бид на 0.03 и 0.01, на
0.02 пусто): она даёт правильный ответ, потому что объём, прошедший ниже 0.02,
по построению означает, что уровень 0.02 был выбран целиком. Претензий нет.

Опасность в реализации: `prior_size_at_002` и «объём сделок на уровне ≤0.02»
должны браться **на один и тот же момент отсчёта** — оба до начала свипа, либо
оба посередине. Смешение (prior из середины свипа, объём за весь свип) даёт
завышение филла в разы. Пример: prior взят после того, как уровень уже съели
(0), объём просуммирован за весь свип (3200) → филл 3200 вместо 200, то есть
упор в наш размер 1000 вместо честных 200.

Отсюда требования к реализации: агрегировать сделки свипа окном
`classify.window_ms`, фиксировать `prior_size` один раз на старте свипа, и
держать на это отдельный тест (`test_queue_model.py`).

### 6.6 Очередь: три числа вместо одного

`prior_size_at_002` (весь уровень перед сделкой) переоценивает очередь впереди
нас: туда попадают заявки, пришедшие **после** нашей виртуальной постановки,
которые по price-time стоят позади. Дополнительно пишутся:

- `queue_ahead_at_placement` — размер уровня в момент постановки;
- `queue_ahead_est` — то же минус атрибутированные отмены на уровне с тех пор.

`our_fill` по умолчанию — консервативная формула ТЗ; две другие модели
пересчитываются офлайн.

### 6.7 Окно подписки: релиз недоопределён, а `gameStartTime` бывает пуст

«gameStartTime − 10 мин … endDate + 30 мин» и «отписываться только при
резолюции» — взаимоисключающие правила релиза. Беру: держим до подтверждённой
резолюции с потолком `discovery.max_subscription_hours` (дефолт 12), иначе
зависшие рынки навсегда съедают слоты. `release_reason` пишет, что сработало.

Практически важнее другое: **у многих киберспортивных подрынков
`gameStartTime` пуст**, особенно на уровне карт. Прошлая версия логгера
провалилась на неверном моменте подписки; при пустом `gameStartTime` новая
логика провалится так же, только иначе. Поэтому: fallback на
`startDate`/`endDate`, подписка сразу при обнаружении, если старт неизвестен, и
поле `game_start_source` ∈ {gamma, inferred, none}. Без него критерий
`observed_during_game ≥ 80%` непроверяем — непонятно, провал это сбора или
отсутствие метаданных.

### 6.8 Undercut выигрывает сравнение политик нечестно

Симуляция не реагирует на нас. В реальности мейкер, чей аск мы подрезали,
подрежет нас в ответ — это его работа. Значит фактические филлы политики
`undercut` были бы заметно хуже смоделированных, а политика «статичный аск на
4×» от реакции контрагента почти не зависит.

Вывод, который надо держать при чтении отчёта: **результат undercut — верхняя
граница, результат статического 4× — более доверенная оценка.** Анализатор
будет печатать это предупреждение прямо в блоке сравнения политик, а не в
сноске.

Смежное: наш размер на выходе (1000 долей, ~$80 при 4×) в опустошённой после
обвала книге не пренебрежимо мал. Твоё же наблюдение — крупнейшая сделка
разгружалась 20 минут шестью кусками — прямое свидетельство, что размер здесь
значим. Модель очереди покрывает «кто перед нами по нашей цене», но не
покрывает «наше присутствие меняет чужие котировки». Полностью это не решается
без реальных заявок. Смягчение: `exit.max_participation` (доля каждой
встречной сделки, дефолт 1.0 = поведение ТЗ) + `depth_bid_total` в каждой
строке для дисконта офлайн.

### 6.9 Шестая политика выхода: хедж по аску близнеца

`1 − paired_ask` — это не абстрактная «нижняя граница справедливой цены», это
**исполнимая цена хеджа**. Купив наш токен за 0.02 и близнеца за `paired_ask`,
получаем полный комплект, который на резолюции стоит ровно $1, независимо от
исхода. При `paired_ask = 0.60` это зафиксированные 1.61× без единого
покупателя на нашей стороне.

Это единственная политика выхода, чья отдача **не зависит от того, придёт ли
кто-то покупать у нас** — а вся твоя проблема выхода состоит ровно в том, что
после обвала бид-сторона пуста. Добавляю `hedge_at_paired_ask` седьмой строкой
в сравнение политик анализатора. Считается целиком из полей, которые ты и так
собираешь (`paired_ask`, `paired_ask_size`, `paired_stale_seconds`), стоит ноль
дополнительного сбора. Ограничения честно моделируются: хедж ограничен
`paired_ask_size`, невалиден при `paired_stale_seconds` выше порога, и требует
merge-транзакции для досрочного выхода в кэш.

### 6.10 `internal_dislocation`: деление на ноль там, где интереснее всего

Метрика ТЗ (`fair_lower_bound / bid_after`) описывает дислокацию книги, и как
таковая осмысленна. Две проблемы:

1. `bid_after` может быть нулём — ровно в самых глубоких обвалах, то есть
   ключевой предиктор становится неопределённым в самых интересных событиях.
   Нужен guard и явное значение-маркер, а не `inf`/пусто.
2. Она не описывает **нашу** экономику: платим мы 0.02, а не `bid_after`.
   Добавляю `dislocation_vs_entry = fair_lower_bound / our_entry_price` — это
   то, что напрямую отображается в ожидаемую отдачу.

Вопрос к твоим историческим цифрам: как `internal_dislocation` считался на
исторических данных объекта? Если `bid_after` там часто был нулём, то «53% его
филлов на дне» — доля по подвыборке, а не по всем филлам.

### 6.11 `entry.min_bid_above`: парантеза выбросила информацию

Формально противоречия нет — «суммарно на 0.08» уточнено скобкой как «лучший
бид ≥ 0.08», реализую как цену (`entry.min_best_bid`, старое имя — алиас).

Но подозреваю, что первая половина фразы была лучше второй. `best_bid ≥ 0.08` —
это одна заявка; пять долей на 0.08 проходят фильтр при мусорной книге.
Нотиональный порог робастнее. Поэтому в каждую строку пишутся
`bid_notional_above_002`, `bid_shares_above_002`, `n_bid_levels_before` — обе
трактовки проверяются офлайн без пересбора.

### 6.12 Отмена виртуальной заявки не описана

Если предусловие перестало выполняться (лучший бид упал до 0.03) — снимаем или
нет? Реальный пассивный мейкер не успевает. Дефолт: **не снимаем**, в строку
пишется `precondition_held_at_fill` (0/1). Ключ
`entry.cancel_when_precondition_breaks: false`.

### 6.13 Выход живёт дольше окна

`closed_by=resolution` невозможен, если выход останавливается на +120 с. Выход
симулируется, пока ассет подписан, то есть до резолюции; на диск это почти не
влияет (`exit.max_quote_moves`, дефолт 200). В `positions` дополнительно
пишутся `exit_vwap_at_window_end` и `filled_size_at_window_end`, чтобы политика
«120 секунд» считалась без пересбора. `exit.follow_up` — дефолт false по ТЗ.
`exit.min_clip_shares` — остаток меньше минимального размера заявки не
считается продаваемым.

### 6.14 `book_vanished` надо ограничить, иначе он утопит данные

Отмена на 0.02 происходит постоянно — любой мейкер, поправляющий котировки.
Без фильтра эта «отладочная» таблица будет на порядки больше основной. Пишем
`book_vanished` только когда у нас лежала виртуальная заявка и классификатор
отнёс сокращение к отмене. Это ровно та группа сравнения, ради которой ты
просил поле.

### 6.15 `target_wallet_traded_here` смещён в сторону желаемого вывода

Флаг ставится в момент записи, но объект может зайти в рынок позже — нужен
поздний апдейт (ещё довод за SQLite).

Важнее: третья группа анализа — «он не зашёл, мы бы да» — как раз та, которую
ты хочешь видеть большой. Её валидность целиком держится на полноте ленты
активности по 4 адресам. **Любой пропуск его сделок перекладывает событие из
группы 1 в группу 3**, то есть ошибка сбора работает в пользу гипотезы.
Поэтому: инкрементальный опрос с курсором, потолок пагинации ~5500 обходится
частотой опроса, и обязательное поле `target_activity_gap_seconds` — группа 3
без него не должна публиковаться как число.

### 6.16 Сетка окна: 76 точек, не 75

`t ∈ {−30, −28, …, +120}` — это (120+30)/2 + 1 = **76** узлов. Критерий
готовности надо читать как 76, иначе он не выполнится никогда.
`window_complete` + `window_truncated_reason` (`resolution`, `unsubscribed`,
`ws_gap`, `process_stop`): резолюция на +40 с даёт легитимно неполное окно.

### 6.17 Что критерии готовности НЕ проверяют

Все семь порогов из ТЗ — про качество сбора, и они выбраны правильно. Но по
суткам нельзя читать PnL: распределение хвостовое (74% в ноль, максимум 44×).
Частота — пуассоновская величина и стабилизируется быстро; средняя кратность
при таком хвосте не стабилизируется на десятках событий вообще. Если за сутки
наберётся 30 событий, число «средний множитель» из отчёта читать нельзя, и
анализатор будет печатать рядом доверительный интервал бутстрапом, чтобы это
было видно, а не подразумевалось.

## 6.18 ПРОВЕРЕНО НА ЖИВОМ API: обнаружение рынков работает не так, как в ТЗ

Ты просил не перепроверять технические детали. Я и не собирался, но коллектор
на живом запуске не нашёл ни одного рынка, и пришлось смотреть. Три факта,
расходящиеся с ТЗ:

1. **`limit=500` игнорируется.** Gamma отдаёт максимум **100** записей за
   запрос при любом limit. Пагинация по признаку «страница короче limit —
   значит последняя» останавливается на первой же странице. Конфиг теперь
   запрещает limit > 100 с явной ошибкой, чтобы это не всплыло снова.

2. **`offset` глубже ~2100 возвращает 422.** Сплошной перебор активных рынков
   ограничен сверху и полным списком не является.

3. **Сплошной перебор киберспорт не находит.** На 2 100 просмотренных активных
   рынков — ноль матчевых подрынков Dota/CS2. Единственное «совпадение» было
   ложным: слаг `will-the-international-court-of-justice-win-the-nobel-peace-prize`
   поймался на паттерн `the-international` из названия турнира. Паттерн убран.

Рабочий способ — **теги площадки**: `dota` (id 100443), `cs2` (100677),
`counter-strike` (100602), запрос `?tag_id=<id>&related_tags=true`. Теги
разрешаются по слагу на старте, id в конфиге не зашиты.

Тег `esports` (64) брать нельзя: с `related_tags` он тянет долгосрочные пропы и
даже обложки MLB The Show. На живой проверке он дал 1 032 «киберспортивных»
рынка, из которых матчевых не было, и они вытеснили из-под потолка подписки
420 рынков.

Отсюда же фильтр по горизонту (`max_horizon_days: 7`): живой матчевый подрынок
закрывается за часы, а «выиграет ли FaZe турнир первого эшелона в 2026» — через
месяцы. Это **не отбор по ликвидности**: тот смещал бы выборку внутри целевой
популяции, а горизонт вычитает то, чего в ней нет вовсе.

**Отдельно, важное для планирования наблюдения.** На момент написания на
Polymarket **нет ни одного живого матчевого подрынка Dota 2 или CS2** — по
тегам находятся 43 рынка, все долгосрочные пропы. Твоя выборка за два месяца
собрана вокруг турниров; вне турнирных окон наблюдать будет нечего. Сутки
работы на пустом календаре дадут нулевой числитель и не проверят ничего, кроме
того, что процесс не падает. Запускать сбор имеет смысл под расписание матчей.

## 8. Порядок работ

## 9. Ограничения по безопасности

Только чтение. Приватных ключей нет, подписи ордеров нет, обращений к
эндпоинтам размещения нет. Виртуальные заявки существуют только в памяти
процесса и в логах. Адреса объекта используются исключительно для чтения
публичной активности через data-api.
