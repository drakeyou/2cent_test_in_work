# Paper-trade simulator для Polymarket — план реализации

Статус: **план, код не написан**. Ждёт ревью по спорным пунктам (раздел 7).

Цель проекта — не «заработать в симуляции», а измерить **знаменатель**: как часто
в live-подрынках Dota 2 / CS2 вообще возникает условие входа. Всё остальное
(PnL, политики выхода) — производное и должно пересчитываться офлайн из
собранных сырых величин.

## 2. Процесс и запуск

Один asyncio-процесс, Python 3.11+. Зависимости коллектора: `httpx`,
`websockets`, `pyyaml`, `pydantic`. Анализатор дополнительно: `pandas`, `numpy`.

```
python run_collector.py --config config.yaml
python export_csv.py   --db state/paper.db --out data/
python analyze_paper.py --db state/paper.db
python tools/replay.py --frames captures/2026-09-19T14.jsonl.gz --db /tmp/replay.db
```

Конкурентные задачи внутри процесса:

| задача | период | что делает |
|---|---|---|
| discovery | `market_discovery.poll_s` (45s) | Gamma, реестр рынков, окно подписки |
| ws_shard × N | постоянно | book / price_change / last_trade_price |
| recorder tick | 2s | снапшоты в кольцевой буфер и в плотное окно |
| checkpoint tick | 60s | чекпоинты +5/10/20/40/60 мин |
| resolution | 1h | `clob.polymarket.com/markets/{condition_id}` |
| reconcile | 60s + отложенный проход +5 мин | `data-api /trades` |
| target_wallet | 5 мин | `/activity` по 4 адресам |
| coverage heartbeat | 60s | агрегация в часовые строки + gap_seconds |

Рестарт: реестр рынков, кэш резолюций, открытые события и открытые виртуальные
позиции лежат в SQLite. При старте — переподписка на весь актуальный список и
строка в `gaps` от `last_heartbeat` до `now` с `reason=process_restart`.

## 3. Различение «сделка на уровне» и «отмена заявок» — главная часть

### 3.1 Что даёт WS и чего не даёт

На канале `market` без авторизации доступны: `book` (полный L2-снапшот, `hash`,
`timestamp`), `price_change` (`changes: [{price, side, size}]`, где `size` — это
**новый абсолютный размер уровня**, а не дельта), `last_trade_price`
(`price`, `side`, `size`, `timestamp`), `tick_size_change`.

Ключевой факт: **`price_change` сам по себе неразличим.** Уровень 0.02 с 500
до 0 — это либо съели, либо сняли. Единственный способ различить — коррелировать
сокращение книги с независимым свидетельством сделки.

### 3.2 Алгоритм (реальное время, провизорная классификация)

Состояние на каждый asset: `book`, очередь `pending_reductions`, счётчик
`trade_credits[side][price] -> [(size, ts)]` с TTL.

**На `last_trade_price`:**
1. Нормализовать сторону в «какая сторона книги пострадала». Сторона тейкера
   SELL → выбиты биды на `price`.
2. `credits[BID][price] += size`, ts запомнить.
3. Немедленно погасить подходящие `pending_reductions` (сделка пришла раньше
   обновления книги — порядок не гарантирован).
4. Если `price <= entry.price`, сторона SELL и у нас лежит виртуальная
   заявка — **вход срабатывает сразу**, `trigger=trade_at_level`. Ждать
   подтверждения книгой нельзя: потеряем состояние «непосредственно до».

**На `price_change` по биду, уровень L, новый размер S:**
- `Δ = old − S`. Если `Δ <= 0` — это добавление, пишем `size_added_at_L`
  (нужно для очереди «позади нас»).
- Если `Δ > 0` — кладём `PendingReduction(L, Δ, ts)` в очередь с дедлайном
  `ts + classify.window_ms` (дефолт 1500). Пытаемся погасить немедленно.

**На дедлайне:**
```
traded    = min(Δ_remaining, доступные кредиты на L в окне ±window_ms)
cancelled = Δ_remaining − traded
```
Пишем строку классификации с `evidence` ∈ {ws_trade, sweep_inferred, none}.

**На `book` (полный снапшот):** состояние сбрасывается, все висящие
`pending_reductions` закрываются как `unknown` — через снапшот классифицировать
нельзя. Счётчик `classify_unknown` — это метрика качества данных, она идёт в
`coverage`.

### 3.3 Три известные дыры и что с ними

**(а) Свип через несколько уровней.** Тейкер, проходящий книгу сверху вниз,
порождает несколько филлов по ценам мейкеров, а `last_trade_price` может
отдать одно сообщение с одной ценой. Тогда сокращения на уровнях ниже
останутся без кредита и будут помечены как отмена — ложно.
Смягчение: если в **одном** сообщении `price_change` сокращён непрерывный
диапазон бидов сверху вниз до уровня L включительно, и на верхней границе
диапазона есть кредит сделки — вся полоса атрибутируется сделке с
`evidence=sweep_inferred`. Это эвристика, не истина, поэтому она живёт в
отдельном поле, а не подменяет `trigger`.

**(б) Двусторонняя отмена.** Маркет-мейкер, снимающий котировки, обычно
трогает обе стороны. Сделка — только одну. Пишем признак
`opposite_side_changed_ms` (сколько мс назад менялась противоположная
сторона). Это **фича для офлайн-анализа**, не правило решения.

**(в) `last_trade_price` может не эмититься на каждый филл.** Утверждать по
памяти, что канал шлёт сообщение на каждую сделку, я не буду. Это проверяется
эмпирически за первые часы (раздел 3.4) и закрывается сверкой.

### 3.4 Самокалибровка стороны на старте

`side` в `last_trade_price` — это сторона тейкера или мейкера, я не полагаюсь
на память. На первых N=200 сделках процесс считает корреляцию: при `side=SELL`
чаще сокращается бид или аск? Результат пишется в `state/calibration.json` и
используется дальше; расхождение логируется. Пока калибровка не набрана,
используется гипотеза «side = сторона тейкера», а события помечаются
`calibration_pending=1`.

### 3.5 Сверка с ончейн-лентой — то, что делает данные доверенными

Раз в 60 секунд и отложенным проходом на +5 минут для каждого рынка с
событиями:

```
GET https://data-api.polymarket.com/trades?market={conditionId}&limit=500&takerOnly=false
```

Дедупликация по (tx_hash, maker, taker, price, size) — при `takerOnly=false`
одна сделка приходит с обеих сторон. Таймстемпы там блочные, с секундной
гранулярностью, поэтому допуск ±3 с, и порядок сделок внутри блока не
восстанавливается.

Для каждого события:
- `trigger=trade_at_level` подтверждено, если в окне есть реальная сделка
  `price <= entry.price` → `trigger_confirmed=1`,
  `confirmed_level_traded_size`;
- `book_vanished` (входа не открывали), но реальная сделка была →
  **ложноотрицательный** классификатор, строка в `reconcile` с
  `verdict=missed_trade`;
- `trade_at_level` без ончейн-подтверждения → `verdict=phantom_trade`.

Анализатор печатает **матрицу ошибок классификатора** как заголовочную
метрику. Если WS-классификация сходится с лентой, скажем, в 97% случаев —
датасету можно верить; если в 70% — весь проект надо пересобирать на ленте, а
не на WS. Без этого числа PnL из симулятора ничего не значит.

### 3.6 Защита от рассинхрона книги

У WS нет пер-ассетных секвенс-номеров, только `hash`, алгоритм которого я
воспроизводить не буду. Вместо этого — периодическая (раз в 5 мин на активный
ассет, с рейт-лимитом) сверка WS-книги с REST-книгой по `token_id`; расхождение
пишется в `book_desync`. Рассинхрон тихо отравляет `prior_size_at_002`, а это
прямо множитель в модели очереди.

## 4. Хранилище: SQLite (WAL) как основное, CSV как экспорт

Схема из ТЗ **сама требует поздних записей в уже написанные строки**:
чекпоинт +60 минут, резолюция, `trigger_confirmed` из сверки,
`target_wallet_traded_here` (кошелёк может зайти в рынок после нашего события).
CSV этого не умеет — получится append-only с патч-строками и грязным merge на
выходе. Плюс: атомарность при падении (оборванная строка CSV = битый файл),
чтение анализатором на живых данных, уникальность `event_id`.

Требование «все новые поля считать при записи» выполняется: производные поля
(`fair_lower_bound`, `book_sum`, `internal_dislocation`, `our_fill`) считаются в
момент записи и хранятся, `export_csv.py` — тупой дамп без пересчёта.

`storage.backend: sqlite | csv` в конфиге, дефолт `sqlite`.

Сырые WS-фреймы: gzip-jsonl **только для окон событий**, хранение
`storage.keep_raw_frames_days: 3`. Это единственный способ переклассифицировать
trade-vs-cancel задним числом, стоит единицы МБ в сутки. Непрерывный лог книги
по всем рынкам — нет, это ровно тот путь, который дал 48 млн снапшотов.

## 5. Окно наблюдения

Сетка плотной записи: `t ∈ {−30, −28, …, +120}` = **76 точек**, не 75
(150 секунд / 2 = 75 интервалов, 76 узлов). Критерий готовности надо читать как
«76», иначе он не выполнится никогда.

Каждое событие несёт `window_complete` и `window_truncated_reason`
(`resolution`, `unsubscribed`, `ws_gap`, `process_stop`) — резолюция на +40 с
даёт легитимно неполное окно, и это не дефект сбора.

Предсобытийная часть (−30…0) берётся из кольцевого буфера (60 с, шаг 2 с).

## 6. Что я реализую иначе, чем в ТЗ, и почему

### 6.1 `prior_size_at_002` — не из снапшота

ТЗ: «в снапшоте непосредственно перед сделкой». При шаге снапшота 2 секунды
«непосредственно перед» — это до 2 секунд устаревания, ровно в самый
турбулентный момент. Книга ведётся пособытийно, `prior_size_at_002` берётся из
состояния на последний апдейт **строго до** таймстемпа сделки. В строку пишется
и `prior_size_staleness_ms`, чтобы видеть, насколько это отличается от
снапшотной версии.

### 6.2 Очередь: три числа вместо одного

`prior_size_at_002` (по ТЗ, весь уровень перед сделкой) переоценивает очередь
впереди нас: туда попадают заявки, пришедшие **после** нашей виртуальной
постановки, которые по price-time стоят позади. Поэтому пишутся также:
- `queue_ahead_at_placement` — размер уровня в момент виртуальной постановки;
- `queue_ahead_est` — то же минус атрибутированные отмены на уровне с тех пор.

`our_fill` по умолчанию считается по консервативной формуле ТЗ; остальные две
модели пересчитываются офлайн.

### 6.3 Дедупликация событий — иначе главное число не определено

В ТЗ нет правила, что считать одним событием. При обвале книги трейдов по
≤0.02 прилетает пачка. Правила:
- одна открытая виртуальная заявка на ассет одновременно;
- дальнейшие сделки по уровню, пока заявка не выбрана целиком, — это
  **дофиллы того же события** (строки в `quotes`/`fills`), а не новые события;
- после полного филла — `entry.cooldown_s` (дефолт 300) до новой постановки;
- `entry.max_events_per_asset_per_hour` как предохранитель от взрыва объёма.

Без этого «событий на рынко-час» — не величина, а артефакт кода.

### 6.4 Два знаменателя, не один

Анализатор печатает частоту в **двух** нормировках:
- на наблюдённый рынко-час (минус `gap_seconds`);
- на рынко-час, **в течение которого держалось предусловие** (best_bid ≥ 0.08).

Это разные вопросы: «как часто бывает обвал» и «как часто бывает обвал там, где
мы вообще стояли бы». Одно число без другого неинтерпретируемо, а заявленная
цель проекта — именно частота.

### 6.5 `entry.min_bid_above` — в ТЗ противоречие

«биды суммарно хотя бы на 0.08» и «лучший бид ≥ 0.08» — это разные условия
(нотионал против уровня цены). Реализую как **цену**: `best_bid >= 0.08`
(ключ `entry.min_best_bid`, `entry.min_bid_above` — алиас). Дополнительно в
каждую строку пишется `bid_notional_above_002`, чтобы вторая трактовка
проверялась офлайн без пересбора.

### 6.6 Отмена виртуальной заявки не описана

Если предусловие перестало выполняться (лучший бид упал до 0.03) — снимаем
заявку или нет? Реальный пассивный мейкер не успевает. Дефолт: **не снимаем**,
заявка лежит; в строку пишется `precondition_held_at_fill` (0/1), чтобы
фильтровать офлайн. Ключ `entry.cancel_when_precondition_breaks: false`.

### 6.7 `internal_dislocation` делит не на то

`fair_lower_bound / bid_after` описывает книгу после сделки, а не нашу
экономику: наша цена входа — 0.02, а не `bid_after`. Пишу оба:
`internal_dislocation` (как в ТЗ) и `dislocation_vs_entry = fair_lower_bound /
our_entry_price`. Второе — то, что реально предсказывает PnL. Плюс защита от
деления на ноль (`bid_after` может быть 0).

### 6.8 Рыночное воздействие не моделируется — и это смещает результат вверх

Наши 1000 долей на входе (~$20) книгу почти не трогают. А вот выход: продажа
1000 долей по 0.08 (4×) в опустошённую после обвала книгу — это уже заметный
объём относительно того, что там стоит. Симулятор по построению **оптимистичен
на выходе**, потому что мы добавляем в ленту размер, которого не было.
Смягчение: `exit.max_participation` (доля каждой встречной сделки, которую мы
можем забрать; дефолт 1.0 = поведение ТЗ) + `depth_bid_total` в каждой строке,
чтобы применить дисконт офлайн. Полностью проблему это не решает — решить её
без реальных заявок нельзя, и это надо держать в голове при чтении итогового
множителя.

### 6.9 Выход живёт дольше окна

`closed_by=resolution` невозможен, если симуляция выхода останавливается на
+120 с. Поэтому выход симулируется, пока ассет подписан, то есть до резолюции;
на диск это почти не влияет (перестановки аска ограничены
`exit.max_quote_moves`, дефолт 200). В `positions` дополнительно пишутся
`exit_vwap_at_window_end` и `filled_size_at_window_end`, чтобы политика
«120 секунд» считалась без пересбора. `exit.follow_up` (следовать за аском
вверх) — дефолт false по ТЗ, но флаг есть.

### 6.10 Окно подписки: в ТЗ противоречие

«подписываться gameStartTime−10м … endDate+30м» и «отписываться только при
резолюции» — взаимоисключающие правила релиза. Беру: держим подписку до
подтверждённой резолюции, но с потолком `discovery.max_subscription_hours`
(дефолт 12), иначе зависшие рынки навсегда съедают слоты подписки.
`release_reason` в `markets` пишет, что сработало.

Отдельно: **у многих киберспортивных рынков `gameStartTime` пуст.** Тогда
критерий готовности «observed_during_game ≥ 80%» непроверяем. Поэтому:
fallback на `startDate`/`endDate`, подписка сразу при обнаружении, если старт
неизвестен, и поле `game_start_source` ∈ {gamma, inferred, none}, чтобы провал
по критерию можно было диагностировать, а не гадать.

### 6.11 Потолок подписок — риск для главного числа

Каждый матч даёт десятки подрынков × 2 токена. 20 параллельных матчей — это
могут быть тысячи `asset_id`. Лимиты CLOB WS на подписку мне неизвестны,
поэтому: шардинг `ws.max_assets_per_conn` (дефолт 100), общий потолок
`ws.max_total_assets`, приоритет по ликвидности/объёму, и — обязательно —
строка в `coverage` на каждый **отброшенный по потолку** рынок. Молчаливый
дроп подписок завышает частоту событий, потому что знаменатель сжимается, а
числитель нет. Это тот же класс ошибки, что и незалогированный разрыв WS.

   ассетов ты готов тянуть.
5. `observed_during_game` при пустом `gameStartTime` — считать наблюдением или
   исключать из знаменателя критерия.

## 8. Порядок работ

1. Каркас: config, storage/schema, discovery, classify, markets-реестр.
2. WS-клиент + book + capture/replay + фикстуры (без этого цикл отладки =
   сутки, а с ними = секунды).
3. `tape.py` — классификатор trade-vs-cancel, тесты на синтетике
   (чистая сделка, чистая отмена, гонка порядка сообщений, свип, снапшот
   посреди события).
4. Виртуальные заявки, модель очереди, recorder, окно.
5. Политика выхода, позиции.
6. Резолюция, сверка с лентой, target_wallet.
7. `analyze_paper.py`, `export_csv.py`.
8. Прогон, проверка критериев готовности, отчёт по матрице ошибок
   классификатора.

## 9. Ограничения по безопасности

Только чтение. Приватных ключей нет, подписи ордеров нет, обращений к
эндпоинтам размещения нет. Виртуальные заявки существуют только в памяти
процесса и в логах. Адреса объекта используются исключительно для чтения
публичной активности через data-api.
