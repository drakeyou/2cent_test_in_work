# Paper-trade симулятор Polymarket

Симулятор пассивных лимитных заявок на 1–2 центах в live-подрынках Dota 2 и
CS2. **Только чтение.** Приватных ключей нет, подписи ордеров нет, обращений к
эндпоинтам размещения нет. Виртуальные заявки существуют исключительно в памяти
процесса.

## Зачем

Цель — не «заработать в симуляции», а измерить **знаменатель**: как часто в
live-подрынках вообще возникает условие входа. Все известные цифры по стратегии
посчитаны по числителю — по позициям одного участника. Сколько раз обвал
случался там, где его не было, неизвестно. Это и есть главное неизвестное
проекта.

## Установка и запуск

```bash
pip install -r requirements.txt
python run_collector.py --config config.yaml     # сбор
python analyze_paper.py --db state/paper.db      # отчёт
python export_csv.py --db state/paper.db --out data/   # CSV по схеме ТЗ
```

Отладка без ожидания живого матча:

```bash
python tools/capture_ws.py --assets <id> --seconds 300 --out captures/x.jsonl
python tools/replay.py --frames captures/x.jsonl --db /tmp/replay.db
python tools/make_synthetic.py --db /tmp/demo.db --events 140   # проверить отчёт
pytest -q
```

## Самая тонкая часть: сделка или отмена

Уровень 0.02, ушедший с 3000 в 0, — это либо съели рыночной продажей (нас бы
залило), либо мейкер снял заявки (наша осталась бы лежать). Из `price_change`
эти случаи неразличимы, а путать их нельзя: половина записей была бы о филлах,
которых не было.

Различаются тремя уровнями:

1. **Реальное время.** `last_trade_price` кладёт «кредит» на уровень, который
   гасит сокращения книги в окне ±1.5 с. Окно двустороннее: порядок сообщений
   не гарантирован. Несопоставленные сокращения откладываются до дедлайна, а не
   решаются сразу.
2. **Эвристика свипа.** Тейкер идёт по книге сверху вниз, а `last_trade_price`
   может отдать одну цену на весь проход. Непрерывная полоса сокращений с
   настоящим кредитом сделки атрибутируется проходу — с отдельной пометкой
   `sweep_inferred`, которая никогда не подменяет `trigger`.
3. **Сверка с лентой** (`data-api /trades`). Даёт истину и матрицу ошибок
   классификатора. **Это заголовочная метрика всего датасета:** пока сходимость
   неизвестна, PnL из симулятора нечем поверить.

Плюс самокалибровка: что означает `side` в `last_trade_price` — сторону тейкера
или мейкера — не предполагается, а измеряется по тому, какая сторона книги
реально сократилась.

## Отличия от исходного ТЗ

Подробно — в [docs/PLAN.md](docs/PLAN.md). Кратко:

| что | почему |
|---|---|
| SQLite вместо CSV | схема ТЗ сама требует поздних записей: чекпоинт +60 мин, резолюция, сверка, флаг объекта |
| событие = жизнь заявки | в ТЗ определения нет, а от него частота меняется на порядок |
| три знаменателя | «как часто бывает обвал» и «как часто там, где мы стояли бы» — разные вопросы |
| `prior_size` пособытийно | из снапшота раз в 2 с он устаревает в самый турбулентный момент; расхождение измеряется в отчёте |
| три модели очереди | ТЗ засчитывает впереди нас заявки, пришедшие позже нашей |
| теневая заявка | кулдаун — произвольная константа; так частота пересчитывается при любом |
| случайная выборка при потолке | отбор по ликвидности выкинул бы тонкие подрынки, где и живёт эффект |
| `dislocation_vs_entry` | метрика ТЗ делит на `bid_after`, а платим мы 0.02; плюс `bid_after` бывает нулём |
| ноль против NULL | пустая бид-сторона — это наблюдение, а не пропуск данных |
| хедж по близнецу | `1 − paired_ask` — исполнимая цена хеджа; единственный выход, которому не нужен покупатель |
| 76 узлов окна | (120 + 30) / 2 + 1, а не 75 |

## Проверено на живом API (расходится с ТЗ)

- Gamma отдаёт максимум **100** записей за запрос, `limit=500` игнорируется;
  `offset` глубже ~2100 даёт 422. Сплошной перебор активных рынков неполон и
  киберспорт не находит (0 совпадений на 2100 рынков).
- Рабочий путь — теги: `dota`, `cs2`, `counter-strike`, через
  `?tag_id=<id>&related_tags=true`. Id разрешаются по слагу на старте.
- Тег `esports` брать нельзя: с `related_tags` тянет долгосрочные пропы и
  обложки MLB.
- **Живых матчевых подрынков Dota/CS2 может не быть вовсе** вне турнирных
  окон. Сутки сбора на пустом календаре дадут нулевой числитель. Сбор имеет
  смысл запускать под расписание матчей.

## Чего симулятор не умеет

- **Не моделирует наше влияние на рынок.** Модель очереди покрывает «кто перед
  нами по нашей цене», но не то, что мейкер, чей аск мы подрезали, подрежет нас
  в ответ. Поэтому результат `undercut` — верхняя граница, а статичный аск на 4×
  более доверителен. Отчёт печатает это в самом блоке сравнения.
- **Не даёт PnL по суткам.** Распределение хвостовое; среднее по десяткам
  событий не стабилизируется. Смотреть на доверительный интервал.
- **Третья группа сверки с объектом смещена в пользу гипотезы:** пропуск его
  сделки перекладывает событие в неё. Без нулевого `target_activity_gap` её
  нельзя публиковать как число.
